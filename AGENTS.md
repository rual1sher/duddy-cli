# 🤖 Duddy — Документация для AI-агентов и разработчиков

## ⛔ ОБЯЗАТЕЛЬНОЕ ПРАВИЛО ДЛЯ ВСЕХ АГЕНТОВ — ЧИТАТЬ ПЕРВЫМ

Этот файл обязан прочитать **целиком** любой агент (Claude Code и его субагенты, agy / Antigravity, Codex, Cursor, Gemini CLI, сам Duddy и любой другой) **до первого действия с файлами или папками проекта**.

1. **Без чтения — только чтение.** Пока файл не прочитан до последней строки, запрещено создавать, изменять, переименовывать, перемещать и удалять любые файлы и папки, а также запускать команды, которые что-то меняют (`npm install`, `git checkout`, `git stash`, форматтеры, генераторы, `rm`, `mv`, `sed -i`). Разрешено только читать и искать.
2. **Дочитывать до конца.** Если инструмент чтения обрезает файл, дочитай его частями. Последний раздел файла — «✅ Чек-лист перед завершением задачи»; если ты его не видел, файл прочитан не полностью.
3. **Не удалось прочитать — остановись.** Сообщи пользователю и ничего не меняй. Работать «по памяти» или угадывать правила нельзя.
4. **Правила файла важнее привычек агента.** Если задача пользователя противоречит этим правилам, спроси пользователя до того, как нарушить правило.
5. **Документация — часть задачи.** Если изменение затрагивает описанное здесь (новый файл, команда, флаг, клавиша, поле конфига, правило, поведение), обнови этот файл в той же задаче.
6. **Подзадачи и субагенты.** Агент, который передаёт работу другому агенту, обязан в задании потребовать сначала прочитать `AGENTS.md`.

Как файл попадает к агентам автоматически: `AGENTS.md` читают agy / Antigravity, Codex и Duddy (`src/projectContext.js`, первые 6 000 символов); Claude Code подключает его через `CLAUDE.md` (строка `@AGENTS.md`). Автоматическая загрузка не отменяет пункт 2: Duddy видит только начало файла и обязан дочитать остальное через `read_file`.

---

> **Duddy** — это легковесный, высокоэффективный консольный AI-ассистент и автономный агент для Linux и DevOps, написанный на Node.js. Он работает через OpenRouter API, Google AI Studio (Gemini API напрямую) и xAI (Grok через официальный OpenAI-совместимый API), а также с локальными моделями Ollama, поддерживая как бесплатные модели, так и коммерческие флагманы вроде Gemini 3.8 Flash, Claude Sonnet 4.6, GPT-4.1, Grok-4.7) и умеет напрямую взаимодействовать с файловой системой проекта.

## 🛠️ Технологический стек

* **Среда выполнения:** Node.js (версия >= 22.0.0, нативная поддержка ES Modules `"type": "module"`).
* **AI Provider / SDK:** `openai` SDK (`baseURL`: OpenRouter `https://openrouter.ai/api/v1`, Google AI Studio `https://generativelanguage.googleapis.com/v1beta/openai/` xAI `https://api.x.ai/v1` или локальная Ollama `${OLLAMA_HOST}/v1/`) с поддержкой Function Calling (Tool Calling), стриминга ответов и отслеживания reasoning-токенов.
* **Терминальный интерфейс (CLI & TUI):**
  * `ink` (v8+) и `react` (v19+) — современный реактивный консольный интерфейс (TUI в стиле Claude Code).
  * `ink-text-input` (v6+) — поле ввода текста и скрытых ключей.
  * `chalk` (v6+) — стилизация и цветной ANSI-вывод.
  * `ora` (v9+) — спиннер для разового (one-shot / pipe) режима.
* **Файловая система:** Нативные `node:fs/promises`, `node:fs`, `node:path`.
* **Стандарты конфигурации:** Linux XDG Base Directory (`~/.config/duddy/config.json`).
* **Голос (внешние программы, не npm-зависимости):** Piper TTS (синтез речи, голос `ru_RU-dmitri-medium`), whisper.cpp `whisper-cli` (распознавание, модель `ggml-base`), запись через `pw-record` (PipeWire) или `arecord` (alsa-utils), воспроизведение через `pw-play` или `aplay`. Бинарники и модели ставит `/voice install` в `~/.config/duddy/voice/`.

## 🏗️ Архитектура проекта

### Архитектура вывода и событий:
Ядро агента полностью отделено от интерфейса: `runAgentTurn` в `src/agent.js` принимает сообщения и `toolCtx`, исполняет цикл взаимодействия с LLM и отправляет типизированные события (`onPhase`, `onModel`, `onText`, `onStepEnd`, `onToolStart`, `onToolResult`, `onWarning`, `onQueuedInjected`), а очередь сообщений забирает через `takeQueued`. В интерактивном режиме эти события принимает хук `src/ui/hooks/useAgentTurn.js`, а `src/ui/App.js` на базе Ink собирает из хуков экран: история, живой вывод, модальные оверлеи (Picker, Approval, SecretInput, BrowserLogin), поле ввода и строка статуса (до первого пользовательского сообщения баннер анимируется через `AnimatedBanner.js`; анимацию можно отключить переменной окружения `DUDDY_NO_ANIMATION=1`). Интерфейс рисуется с верха экрана (`startAtTop` при старте, `clearScreenToTop` при /clear, смене темы и ресайзе). Пока история помещается на экран, она рисуется в динамической области высотой в экран, и поле ввода со строкой статуса прижаты к низу; как только история с живым выводом перестаёт помещаться (замер `measureElement` в `App.js`), она переносится в Ink `Static` и дальше экран прокручивается как обычно; альтернативный экран не используется, прокрутка терминала сохраняется. В неинтерактивном разовом или пайплайн-режиме (`bin/duddy.js`) события обрабатывает `src/plainRenderer.js` с прямым потоковым выводом в `process.stdout` без запуска React/Ink.

### Схема работы агентного цикла (Agent Loop)

```
[ Пользовательский ввод ] 
          │
          ▼
    [ src/ui/hooks/useAgentTurn.js ] ──► Формирует messagesToSend (system + history + user)
          │
          ▼
   [ src/agent.js ] ──► Запрос в LLM API (streamChatCompletion + AGENT_TOOLS)
          │
     ┌────┴─────────────────────────────┐
     │                                  │
     ▼ (tool_calls)                     ▼ (content)
[ Исполнение инструментов ]       [ events.onText ] ──► Живой стриминг в TUI / plainRenderer
 [ src/tools/execute.js ]               │
     │                                  ▼
     ├─► ctx.approve / автоподтверждение [ events.onStepEnd / Завершение хода ]
     │   fs.writeFile / readFile / etc.
     │
     ▼
[ Возврат результата (role: 'tool') ]
     │
     └────► Повторный виток цикла в API ──► Модель формирует финальный ответ
```

## ⚙️ Система инструментов (Tool Calling)

Duddy поддерживает выполнение операций с файловой системой в раздельных режимах безопасности: безопасные операции чтения и структуры выполняются автономно, а операции записи и удаления требуют подтверждения пользователя:

| Инструмент | Параметры | Описание | Режим |
| :--- | :--- | :--- | :--- |
| `create_file` | `path`, `content` | Создает новый файл или перезаписывает существующий (автоматически создавая папки). Защищен от передачи пути к папкам (`EISDIR`). Не перезаписывает файлы длиннее `MAX_CHARS` и файлы не в UTF-8. Перед запросом подтверждения показывает изменённый блок или начало нового файла (до 12 строк). | Подтверждение |
| `create_folder` | `path` | Создает папку (включая все промежуточные подпапки `recursive: true`). | Автономно |
| `read_file` | `path`, `start_line`, `max_lines`, `offset` (опц.) | Читает текстовое содержимое файла порциями до 40 000 символов для защиты от раздувания контекста, можно только нужные строки. Порция заканчивается на границе строки, в конце указано, как продолжить. Бинарные файлы не читает. Возвращает чистый текст без JSON-экранирования. | Автономно, для секретов подтверждение |
| `edit_file` | `path`, `old_content`, `new_content` | Точечно заменяет фрагмент `old_content` на `new_content` в существующем файле. Отказывается менять файлы не в UTF-8. Перед запросом подтверждения выводит дифф (до 12 строк). | Подтверждение |
| `delete_file` | `path` | Удаляет файл из файловой системы. Символические ссылки удаляются без разыменования целевого файла (`followFinalSymlink: false`). | Подтверждение |
| `delete_folder` | `path` | Рекурсивно удаляет папку со всем содержимым (защищен от удаления корня `.`, отклоняет удаление симлинков). Перед подтверждением выводит число элементов. | Подтверждение |
| `list_dir` | `path` (опц.) | Возвращает список файлов и директорий с иконками 📁/📄. | Автономно |
| `bash` | `command`, `timeout_seconds` (опц.) | Выполняет команду в рабочей папке без терминала, по умолчанию до 120 с, максимум 600. Возвращает начало и конец вывода, при ненулевом коде результат начинается с `Ошибка: код выхода N`. | По политике `classifyCommand` |
| `grep` | `pattern`, `path`, `glob`, `case_insensitive`, `literal` | Ищет по содержимому через `rg` в режиме `--smart-case`, до 100 совпадений и 12 000 символов. Совпадения из файлов с секретами скрываются целиком, показывается только их число. | Автономно |
| `glob` | `pattern`, `path` | Ищет файлы по шаблону имени через `rg --files`, до 200 путей, учитывает `.gitignore`. | Автономно |

### Принцип автономности и подтверждения
* Безопасные операции (`create_folder`, `read_file`, `list_dir`) исполняются автономно по запросу модели. `read_file` для путей с секретами требует подтверждения.
* Опасные операции модификации и удаления (`create_file`, `edit_file`, `delete_file`, `delete_folder`) требуют подтверждения пользователя через интерактивный диалог (`Да`, `Да, и не спрашивать до конца сессии`, `Нет` — горячие клавиши `y` / `a` / `n` / `Esc`).
* В неинтерактивном окружении (без TTY или в пайпе) при отсутствии флага `--yes` опасные действия автоматически отклоняются с предупреждением.
* Флаг `-y, --yes` включает сквозное автоподтверждение (`autoApprove: true`) без остановок на диалоги, кроме путей с секретами.
* **Режимы разрешений (`Shift+Tab`):** состояние хранится в `ctx.mode` (`default`, `acceptEdits`, `plan`, `auto`) и настраивается через `applyMode`. В режиме `plan` применяется двойная защита (double enforcement): инструменты записи скрываются из схемы модели (`toolsForMode`), а при попытке вызова блокируются на уровне `executeTool` с предупреждением в лог; в `bash` при `plan` разрешены только команды класса `safe`, остальные отклоняются без запроса подтверждения.
* Пути с секретами (`classifyPath` возвращает `sensitive`) подтверждаются отдельно при каждом обращении: `requestApproval` игнорирует `autoApprove`, в диалоге нет варианта «на всю сессию», по умолчанию выбрано «Нет», а Enter в разовом режиме означает отказ. Без терминала такой доступ отклоняется.
* Результат выполнения (успех, отмена пользователем или ошибка) немедленно отображается в консоли и возвращается в контекст агента.

## 📜 Общие правила и соглашения разработки

### 1. Экономия токенов и управление контекстом
* **Никакой воды и приветствий:** Системный промпт (`DEFAULT_SYSTEM_PROMPT` в [`src/config.js`](src/config.js)) запрещает модели использовать вступительные и заключительные фразы ("Конечно!", "Вот ваше решение:", "Надеюсь, это помогло!").
* **Автоматическая адаптация стиля:** Стиль ответа выбирается моделью автоматически (ADAPTIVE MODE в `DEFAULT_SYSTEM_PROMPT`), системный промпт не хранится в конфиге.
* **Сжатый вывод результатов инструментов:** Инструменты возвращают понятный модели чистый текст (plain text), а не многократно экранированный JSON, экономя токены промпта.
* **Ограничение истории:** В `src/history.js` хранится история последних 10 ходов пользователя (`MAX_HISTORY_TURNS = 10`), что гарантирует сохранение контекста вызова инструментов и не разрывает пары assistant.tool_calls ↔ tool. Для предотвращения раздувания контекста результаты `tool` из предыдущих ходов длиннее 4000 символов обрезаются до 4000 символов с пометкой об обрезке. Результаты текущего хода не обрезаются, кроме случая отказа провайдера (см. раздел 3). Пересказа старых ходов нет.
* **Рост расхода:** Каждый шаг заново отправляет всё накопленное, поэтому расход хода растёт квадратично. `compactToolResults` (`src/llm/compact.js`) перед каждым запросом проверяет бюджет `TOOL_RESULT_BUDGET` и заменяет старые результаты заглушкой до `TOOL_RESULT_TARGET`. Результаты последнего шага не трогаются. Разрыв между бюджетом и целью нужен, чтобы сжатие было редким: оно меняет начало запроса и сбрасывает кэш провайдера. Убранный файл удаляется из `ctx.fullyRead` и `ctx.seenReads`: модель его больше не видит, поэтому перезапись снова требует чтения.
* **Повторное чтение:** `read_file` с тем же хешем файла и теми же параметрами в пределах хода возвращает короткий ответ вместо содержимого (`ctx.seenReads`, `ctx.fullyRead`).
* **Аргументы записи:** `trimToolResults` заменяет в истории длинные строки в аргументах вызовов заглушкой. Вызовы с `extra_content` (подпись Gemini) не меняются.
* **Контекст проекта:** `buildProjectContext` считается один раз в `bin/duddy.js` и дописывается к системному промпту. Его нельзя пересчитывать в ходе сессии: начало запроса должно быть стабильным для кэша. Список файлов сворачивается по папкам, если их больше 150. Инструкции обрезаются до 6 000 символов и не попадают в промпт, если похожи на секрет или ведут по симлинку наружу. Файлы инструкций приходят из репозитория, поэтому оформлены как заметки и не отменяют правил безопасности.
* **Кэш:** для `anthropic/*` через OpenRouter в запрос добавляется `cache_control` на верхнем уровне, для OpenRouter ещё `session_id` (`session.id`), чтобы запросы шли к одному провайдеру. Остальные провайдеры кэшируют сами.
* **Учёт токенов:** `runAgentTurn` возвращает `turnUsage` за все шаги, `formatTurnUsage` показывает его в итоге хода. Строка статуса показывает размер контекста по последнему шагу.
* **Лимит шагов:** Один ход выполняет не больше 10 шагов с инструментами (`MAX_TOOL_TURNS` в `src/agent.js`), затем останавливается с предупреждением.
* **Контекст:** Команда `/context` (`contextLines`) выводит заполнение окна текущей модели (`contextLength - lastTokens`) и историю ходов. `/clear` сбрасывает `session.lastUsage`, иначе отчёт показывал бы размер старого диалога.
* **Лимиты:** Команда `/usage` (`usageLines`) выводит активную модель сверху, затем остальные модели по провайдерам. Таблиц лимитов в коде нет, потому что провайдеры не отдают их через API, а числа зависят от тарифа: показывается только увиденное (данные ключа OpenRouter, заголовки `x-ratelimit-*`, отказы 429, счётчики Duddy). `/usage` не обращается к моделям и берёт список из `catalogCache`: `listModels` может запустить пробинг, а он тратит квоту.
* **Запись лимитов (`src/models/limits.js`):** `runAgentTurn` файл не пишет, он сообщает о запросе через событие `onRequestDone`, а пишут `plainRenderer` и `useAgentTurn`. Иначе тесты агента писали бы в настоящий конфиг. Текст ошибок не сохраняется, потому что в нём бывают идентификаторы проекта.

### 2. Безопасность файловых операций
* **Ограничение рабочей папкой:** Все пути проверяются через асинхронную функцию `resolveSafePath(targetPath, { followFinalSymlink })` относительно канонического корня проекта (`await fs.realpath(process.cwd())`).
* **Защита от Directory Traversal и побега через симлинки:** Определяется реальный путь (`fs.realpath`) ближайшего существующего предка и проверяется, что итоговый путь не выходит за пределы `root`. Выход за пределы рабочей папки блокируется ошибкой доступа.
* **Обработка симлинков:**
  * Для операций удаления (`delete_file`, `delete_folder`) параметр `followFinalSymlink` отключен (`false`): для проверки берется `realpath` родителя + `basename`, что позволяет безопасно удалять сам симлинк без разыменования целевого файла.
  * Для `delete_folder` действует строгий запрет на удаление корня (`relPath === '.'`), а при обнаружении симлинка через `fs.lstat` операция отклоняется с требованием удалить ссылку через `delete_file`.
* **Валидация перед подтверждением:** Запрос подтверждения у пользователя (`requestApproval`) вызывается строго после всех проверок валидности (существование, соответствие типа папка/файл, успешное нахождение заменяемого блока через `fuzzyReplace`), но до физической записи на диск.
* **Безопасность конфигурации:** Директория `~/.config/duddy` создается с правами `0o700`, а файл `config.json` сохраняется и проверяется с правами `0o600` (защита API-ключа от несанкционированного чтения другими пользователями системы).
* **Лимит чтения:** Чтение файлов лимитировано (`MAX_CHARS = 40000`) на один вызов, чтобы исключить вылет по переполнению контекста модели. Остальное читается через `offset`, склейка порций даёт файл без потерь.
* **Защита от потери данных:** `create_file` отказывается перезаписывать файлы, которые модель не могла прочитать целиком и без искажений (длиннее `MAX_CHARS` или не в UTF-8). `edit_file` не пишет файлы не в UTF-8, иначе байты превратились бы в U+FFFD. Перед записью файл читается заново: если он изменился, пока открыт диалог подтверждения, запись отменяется.
* **Команды (`src/tools/bashTool.js`, `commandPolicy.js`):** `classifyCommand` возвращает `safe` (без вопросов), `ask` (подтверждение), `dangerous` (подтверждение каждый раз, `requestApproval` с `sensitive`) или `forbidden` (отказ без диалога). Перед проверкой снимаются кавычки и экранирование. Список опасных команд не является границей безопасности: песочницы нет, граница — подтверждение пользователя. Поэтому `safe` пополняется только командами, которые ничего не меняют и не выводят содержимое файлов (`cat` туда нельзя), а шаблоны `safe` привязаны к началу и концу строки.
* **Подтверждение команд:** ответ «на всю сессию» для файлов (`ctx.autoApprove`) команды не покрывает, для этого `requestApproval` получает `commandKey`. Ответ `a` запоминает точный текст команды в `ctx.allowedCommands`, который очищает `/clear`. Флаг `--yes` включает `ctx.allowCommands` и пропускает только уровень `ask`.
* **Запуск команд:** окружение очищается от ключей (`SECRET_ENV`), чтобы `env` их не показал. Команда идёт в своей группе процессов (`detached`), остановка по таймауту, `Esc` (`ctx.signal`) и завершение bash отправляют сигнал всей группе, через 2 с упрямые процессы получают `SIGKILL`. Вывод хранится как начало и конец, поэтому память ограничена. Перед отправкой модели вывод проверяется через `scanSecrets`, подтверждённый секрет не попадает в историю (`meta.secret`).
* **Вставка в TUI:** Ink передаёт вставку слушателям `usePaste`, а если их нет, отдаёт её в `useInput`. `InputBox` отключает свой `usePaste`, пока открыт оверлей. `SecretInput` слушает вставку сам, потому что `ink-text-input` работает только с `useInput`. `Approval` слушает её вхолостую: иначе текст `y` из буфера подтвердил бы действие.
* **Поиск и секреты:** `grep` и `glob` не требуют подтверждения, поэтому `grepFiles` проверяет каждый файл с совпадениями целиком через `classifyPath` и `scanSecrets`: строка base64 из тела ключа сама на секрет не похожа. Непроверенный файл считается секретным. Явная цель поиска с секретами отклоняется. Правило `--glob=!.git` идёт после фильтра модели: у `rg` приоритет за более поздним правилом, а шаблон `**` заходит в скрытые папки.
* **Секреты (`src/tools/sensitivePath.js`):** `classifyPath(fullPath, realPath)` проверяет и путь из запроса, и настоящий путь после разрешения симлинков, по абсолютному пути и без учёта регистра. `sensitive` — имена и расширения файлов с секретами и каталоги вроде `.ssh`, `.aws`. `forbidden` — `.config/duddy`, доступ закрыт всем инструментам, подтверждение не помогает. Проверка выполняется в `resolveTarget`, поэтому новые файловые инструменты получают её автоматически, но `sensitive` нужно передать в `requestApproval`. Содержимое подтверждённого файла остаётся в истории сессии и уходит провайдеру.
* **Сканирование содержимого (`src/tools/secretScan.js`):** `scanSecrets(chunk)` сканирует текст на паттерны секретов (токены, ключи API, приватные ключи) — файл с обычным именем тоже может содержать секрет. При обнаружении `read_file` запрашивает отдельное подтверждение. `meta.secret` в ответе инструмента указывает агенту заменить содержимое на заглушку `SECRET_REMOVED` в `newMessages`.
* **`ctx.fullyRead`:** карта `fullPath → sha256` файлов, прочитанных целиком в текущем ходе. Сбрасывается на каждый ход в `runAgentTurn`. `create_file` сверяет хеш с текущим содержимым файла перед перезаписью: перезапись файла, который модель не прочитала в этом ходе, блокируется с ошибкой.
* **Атомарный `saveConfig`:** запись в `config.json` выполняется через временный файл с последующим `rename`. Если существующий `config.json` не является валидным JSON, перед перезаписью он переименовывается в `config.json.broken-<timestamp>` с правами `0o600`. Если переименование невозможно (например, папка недоступна для записи), сохранение прерывается и файл остаётся нетронутым.

### 3. Обработка потокового вывода и рассуждений (Reasoning)
* Модели с длинной цепочкой рассуждений (DeepSeek R1, Nemotron и др.) передают свои мысли либо в `delta.reasoning`, либо внутри тегов `<think>...</think>` и `<thought>...</thought>`.
* Во время рассуждений спиннер не должен гаснуть: в TUI он показывает фазу `Рассуждает…`, в разовом режиме `Duddy рассуждает…`.
* Теги рассуждений обрабатываются потоковым фильтром (`createThinkFilter` в `src/llm/thinkFilter.js`), который не теряет тег, разделённый сетью между чанками.
* В разовом режиме заголовок ответа `╭─ ✦ Duddy` печатается только при поступлении первого значащего (непустого) символа ответа.
* Таймаут первого чанка (`FIRST_CHUNK_TIMEOUT_MS`, 10 минут) и таймаут обрыва потока (`STREAM_STALL_TIMEOUT_MS`, 10 минут — лимит тишины между чанками) действуют на каждый запрос к модели, не означают перегрузку и не ставят метку busy; `commitFailedTurn` сохраняет ход и при ошибке, и при Esc, а при отказе провайдера (4xx) сразу обрезает результаты инструментов.
* **Известная проблема:** глобальный `fetch` в Node имеет `bodyTimeout` 5 минут (`UND_ERR_BODY_TIMEOUT`), и после прихода заголовков он срабатывает раньше `STREAM_STALL_TIMEOUT_MS`. Встроенный `fetch` не даёт изменить этот лимит, нужен свой dispatcher из пакета `undici`.
* Gemini через OpenAI-совместимый эндпоинт отдаёт вызов инструмента одним чанком и не шлёт пинги: заголовки приходят с первым чанком, а до него идёт полная тишина. Поэтому отличить долгую генерацию от зависания по потоку нельзя. xAI также отдаёт вызов функции одним чанком, мысли в `delta.reasoning_content`, Chat Completions у них legacy; модели xAI не проверяются пробингом, потому что это тратит кредиты.
* При обрыве уже напечатанный текст сохраняется в истории с пометкой `(ответ оборван)`; после Esc оставшиеся вызовы шага не выполняются и получают результат `Отклонено`, чтобы не разрывать пары assistant.tool_calls ↔ tool.

### 4. Стандарты добавления новых команд
* Все новые слеш-команды регистрируются в массиве `AVAILABLE_COMMANDS` в [`src/session-actions.js`](src/session-actions.js).
* Обработчик команды добавляется в `handleCommand` в [`src/ui/hooks/useCommands.js`](src/ui/hooks/useCommands.js).
* Команды поддерживают быстрый выход по `Esc` без падения процесса.
* Короткие имена (`/m`, `/v`, `/q`, `/ctx` и др.) задаются в `COMMAND_ALIASES` в `useCommands.js`. Новый алиас не должен совпадать с существующей командой.
* Во время ответа модели команды не выполняются: `handleSend` в `useAgentTurn.js` отвечает предупреждением.
* **Текущие команды:**

| Команда | Алиасы | Что делает |
| :--- | :--- | :--- |
| `/update` | `/upgrade` | Обновить Duddy до последней версии без git clone (через GitHub Releases). |
| `/voice` | `/v`, `/tts`, `/stt`, `/speak` | Без аргумента — запись с микрофона и отправка распознанного текста. `on` / `off` — авто-озвучка ответов (`voiceAutoSpeak`). `status` — что установлено. `install` (`setup`) — скачать Piper, whisper.cpp и модели. |

| `/login [провайдер]` | `/auth`, `/key` | Без аргумента — меню входа. `ollama` / `local` — локальная Ollama (`connectOllama`), `google`, `xai`, `openrouter`. |
| `/clear` | `/cls`, `/reset` | Очистить историю и экран. |
| `/context` | `/ctx` | Заполнение окна контекста. |

* **Клавиши TUI (`App.js`, `InputBox.js`):** `Shift+Tab` — режим разрешений; `Esc` — прервать ответ / очистить ввод / остановить озвучку / отменить запись голоса; `Ctrl+C` — закрыть оверлей или прервать ответ, дважды — выход; `Ctrl+S` — начать запись голоса, повторно (или `Enter`) — закончить и отправить, во время озвучки — остановить её; `Ctrl+V` — вставить изображение из буфера.
* **Флаги CLI и подкоманды (`bin/duddy.js`):** `duddy update` — обновить Duddy до последней версии; `-y, --yes` — автоподтверждение; `-s, --speak` — озвучивать ответы (в TUI и в разовом режиме); `-h, --help`; `-v, --version`. Переменная `DUDDY_NO_UPDATE_CHECK=1` отключает фоновую проверку обновлений при старте.

### 5. Архитектура провайдеров AI (src/providers.js)
* **Мультипровайдерность:** Duddy поддерживает OpenRouter, Google AI Studio напрямую через OpenAI-совместимый API (`v1beta/openai/`) и xAI напрямую через OpenAI-совместимый API (`https://api.x.ai/v1`). Модели xAI не проверяются пробингом, потому что это тратит кредиты. Ollama (`local: true`) работает без ключа: `getProviderKey` возвращает заглушку, модели берутся из `/api/tags` с таймаутом 1,5 с, а если Ollama не запущена, группа просто не попадает в `/model`. Адрес сервера — `ollamaHost()` из `OLLAMA_HOST`. Моделям без capability `thinking` не отправляется `reasoning_effort` (Ollama отвечает на него 400), модели без `tools` помечаются недоступными (`notools`).
* **Конфигурация:** В `PROVIDERS` описаны параметры каждого провайдера: `baseURL`, заголовки, поля ключа в конфиге (`apiKey`, `googleApiKey`, `xaiApiKey`) и переменные окружения (`OPENROUTER_API_KEY`, `GEMINI_API_KEY`, `GOOGLE_API_KEY`, `XAI_API_KEY`).
* **Приоритет ключей:** `getProviderKey` сначала проверяет переменные окружения провайдера, затем поле в `config.json`.
* **Автоопределение:** Функция `detectProviderForModel` определяет провайдера по названию модели (модели, начинающиеся с `gemini-` или `gemma-` без `/`, направляются в Google AI Studio; модели, начинающиеся с `grok-` без `/`, направляются в xAI; остальные — в OpenRouter). Модели Ollama по имени не отличить (`llama3.2:3b`, `user/model:tag`), поэтому `/model <id>` сначала ищет провайдера в каталоге (`findModel`).
* **Смена провайдера:** При переключении модели или авторизации обновляются `session.provider`, `session.apiKey` и сохраняются в `config.json`.
* **Ollama — выбор и вход:**
  * Префиксы `ollama/` и `ollama:` в id модели явно означают Ollama (`detectProviderForModel`, `selectModel`, `changeModel`); префикс отрезается перед сохранением.
  * `/model <id>` без префикса: сначала `findModel` в каталоге, затем `checkOllamaServer()` (совпадение по id или началу id), иначе `detectProviderForModel`.
  * Вход в Ollama (`/login ollama` и пункт меню входа) идёт только через `connectOllama(session)` в `src/session-actions.js`. Она выбирает `runningModels[0] || models[0]` через `selectModel`. Если сервер не запущен или моделей нет, возвращает `{ ok: false }` и **ничего не меняет** в сессии и конфиге — иначе облачная модель осталась бы привязана к провайдеру Ollama и запросы падали бы.
  * `selectModel` с пустым id (в том числе `ollama` без текущей Ollama-модели) возвращает `ok: false` и ничего не сохраняет.
  * Каталог Ollama не кэшируется (`loadProviderModels` пропускает кэш, `pickModel` вызывает `clearCatalogCache('ollama')`): список моделей и отметка «запущен (ps)» из `/api/ps` всегда свежие.
  * Ошибки Ollama не помечают модели недоступными (`getUnavailableReason` и `noteModelError` возвращают `null` для `ollama`): локальная модель может заработать после перезапуска сервера.

### 6. Статусы моделей (src/models/status.js)
* **Файл статусов:** `~/.config/duddy/models-status.json` хранит недоступные модели (7 дней) и перегруженные (15 минут).
* **Недоступные модели** видны в `/model` серыми и не выбираются. Настоящие ошибки 500/502/503/504 ставят метку busy, таймаут её не ставит.

### 7. Изображения и очередь сообщений
* **Вложения:** `src/images.js` читает буфер обмена (`wl-paste`, `xclip`) и вставленные пути. Лимиты: `MAX_IMAGES_PER_MESSAGE = 5`, `MAX_IMAGE_BYTES` 5 МБ, форматы PNG, JPEG, WebP, GIF.
* **Подписи:** `[Изображение #N]` удаляется только целиком (`removeBrokenLabels`), вместе с подписью исчезает вложение. Изображения из старых ходов заменяются заглушкой (`MAX_IMAGE_TURNS = 3`).
* **Очередь:** Сообщения, написанные во время ответа, попадают к модели после шага с инструментами (`takeQueued`) или отправляются после хода. При ошибке и Esc они возвращаются в поле ввода.

### 8. Тесты
* Запускаются через `npm test` (`node:test`, без зависимостей, файлы в `test/`).
* Сеть подменяется через `globalThis.fetch`, поэтому низкоуровневые таймауты Node тесты не покрывают. `HOME` в тестах моделей, конфига, Ollama (`test/ollama.test.js`) и голоса (`test/voice.test.js`) подменяется, настоящий `~/.config/duddy` они не трогают (правило для новых тестов — в разделе 11).
* Диалог подтверждения файловых операций покрыт `test/approval-ui.test.js`. Генерация пиксель-арта котёнка и баннера покрыты `test/banner.test.js`. Остальное поведение TUI (рендеринг, ресайз, оверлеи) проверяется вручную.

### 9. Цветовые темы оформления (src/theme.js)
* Все цвета интерфейса приходят из `theme()` / `paint()`, прямые hex-литералы вида `#[0-9a-f]{6}` за пределами `src/theme.js` запрещены (кроме тестов). В компонентах TUI `theme()` читается во время рендеринга, чтобы смена темы применялась реактивно.

### 10. Голос: STT и TTS (src/voice/)
* **Где лежит:** всё в `~/.config/duddy/voice/` (`VOICE_DIR`): `piper/` (бинарник `piper` и его библиотеки), `whisper/` (`whisper-cli` и `libwhisper`/`libggml`), `models/` (`ru_RU-dmitri-medium.onnx`, `ru_RU-dmitri-medium.onnx.json`, `ggml-base.bin`). Пути вычисляются в `paths.js` из `os.homedir()` при импорте модуля.
* **Готовность:** `isVoiceAvailable()` требует все пять файлов: `piper`, `whisper-cli`, `.onnx`, `.onnx.json`, `ggml-base.bin`. Без `.onnx.json` Piper не запускается, поэтому конфиг голоса проверяется наравне с моделью.
* **Установка (`installer.js`):** только Linux x86_64 (иначе понятная ошибка). Все загрузки асинхронные: `fetch` + `pipeline(Readable.fromWeb(...), createWriteStream)` во временный `.tmp`, затем `rename`; при ошибке `.tmp` удаляется. Архивы распаковываются через `spawn('tar', ...)` без shell. **Нельзя** использовать `execSync`, `spawnSync` и `stdio: 'inherit'` в коде, который вызывается из TUI: синхронный вызов замораживает Ink (интерфейс не перерисовывается, `Ctrl+C` не работает), а `inherit` печатает поверх интерфейса. Каждый файл модели проверяется и докачивается отдельно.
* **Запись (`stt.js`):** `recordAudio(path, { maxDurationMs })` запускает `pw-record` (или `arecord`, если `/usr/bin/pw-record` нет) с 16 кГц, моно, s16 и резолвит `true`, если файл больше 100 байт. Остановка — `stopRecording()` (SIGINT, чтобы рекордер дописал заголовок WAV).
* **Порядок «стоп → распознать»:** после `stopRecording()` обязательно дождаться промиса `recordAudio` и только потом вызывать `transcribeAudioFile`. Иначе whisper читает недописанный WAV и возвращает пустой текст.
* **События дочерних процессов:** если программа не запустилась (нет бинарника), Node шлёт `error`, а затем ещё и `close`. Обработчик `close` у такого процесса нужно пропускать (флаг `spawnFailed`), иначе запасной `arecord`/`aplay` будет считаться завершённым сразу после старта. Ссылки `activeRecorder` / `activePiper` / `activePlayer` обнуляются только если указывают на тот же процесс (`if (activePiper === piper)`), иначе завершение старого процесса потеряет ссылку на новый и его нельзя будет остановить.
* **Распознавание:** `whisper-cli -m <модель> -f <wav> --language auto -nt --no-prints`, маркеры вида `[BLANK_AUDIO]` вырезаются.
* **Озвучка (`tts.js`):** `speak(text)` останавливает предыдущую речь, чистит текст `cleanTextForSpeech`, пишет WAV через Piper (текст в stdin) и проигрывает `pw-play` / `aplay`. Временные файлы удаляются в любом исходе. `speak` никогда не бросает: при любой ошибке резолвит `false`.
* **Очистка текста (`cleanText.js`):** блоки кода заменяются на «[блок кода пропущен]», ссылки — на текст ссылки, URL удаляются. Маркеры `*` и `_` снимаются только на границах слов: `my_var_name`, `config_file.js` и `2 * 3 * 4` должны оставаться как есть (покрыто тестами).
* **Интерфейс:** `/voice` без аргумента открывает оверлей `{ kind: 'recording', onResolve, onCancel }`; `Enter` / `Ctrl+S` вызывают `onResolve` (стоп и распознавание), `Esc` и `Ctrl+C` — `onCancel`. Распознанный текст уходит в `handleSend`. Запись автоматически заканчивается через 25 с. Озвучка останавливается при новой отправке, `Esc`, прерывании ответа (`abort`) и `Ctrl+S`.
* **Авто-озвучка:** `session.autoSpeak` берётся из `config.voiceAutoSpeak` или флага `-s`. В TUI ответ озвучивается после успешного хода (`useAgentTurn`), в разовом режиме — после «✔ Готово» в `bin/duddy.js`. Если голос не установлен, показывается подсказка `/voice install` (при старте TUI, при `/voice on`, в разовом режиме).
* **Ограничения:** запись и воспроизведение на macOS (`rec`, `afplay`) и Windows (`ffmpeg`, PowerShell) есть в коде, но автоустановки для них нет и вручную они не проверялись.

### 11. Порядок работы агента в этом репозитории
* **Сначала прочитать.** См. «⛔ Обязательное правило» в начале файла. Перед правкой файла прочитай сам файл и места, где используется изменяемая функция (`grep` по имени).
* **Git:** без прямой просьбы пользователя не делать `git commit`, `git push`, `git reset --hard`, `git checkout -- <файл>`, `git stash`, `git clean`, не переписывать историю. Коммит в `master` — только через ветку, если пользователь не сказал иначе.
* **Настоящий конфиг пользователя неприкосновенен.** Не читать, не менять и не удалять ничего в `~/.config/duddy/` (ключи API, статусы, голосовые модели) — ни руками, ни через тесты, ни через запуск `duddy`. Чтобы убедиться, что тесты его не трогают: `stat -c %Y ~/.config/duddy/config.json` до и после `npm test` должно совпадать.
* **Зависимости:** не добавлять npm-пакеты и не менять `package.json` / `package-lock.json` без согласия пользователя. Внешние программы (как Piper и whisper) скачиваются только по команде пользователя.
* **Стиль кода:** ES modules, Node >= 22; UI на Ink через `React.createElement` (`const h = React.createElement`), без JSX и без сборки; комментарии и JSDoc на русском; тексты для пользователя на русском; цвета только из `theme()` / `paint()`; файловые операции агента — только через `resolveSafePath`.
* **Синхронные вызовы:** в коде, который работает внутри TUI, не использовать `execSync`, `spawnSync`, `readFileSync` больших файлов и любые долгие синхронные операции.
* **Тесты:** любой новый тест, который прямо или косвенно вызывает `saveConfig`, `selectModel`, `connectOllama`, `installVoice`, `markModelUnavailable`, `recordRequest` или читает пути из `os.homedir()`, обязан подменить `process.env.HOME` на временную папку **до** импорта модулей из `src/` и импортировать их динамически (`await import(...)`), как в `test/config.test.js`, `test/ollama.test.js`, `test/voice.test.js`. Сеть мокается через `globalThis.fetch` и восстанавливается в `afterEach`. Тест не должен запускать настоящие `piper`, `whisper-cli`, микрофон или динамики.
* **Проверка перед сдачей:** `npm test` (все тесты зелёные), `node --check` для изменённых файлов, `node bin/duddy.js --help` запускается. Поведение TUI (оверлеи, клавиши, голос) тестами не покрыто — в отчёте прямо сказать, что проверено вручную, а что нет.
* **Отчёт пользователю:** что изменено по каждому пункту, что не проверено, какие команды запускались и с каким результатом. Не писать «готово», если тесты падают.

### 12. Версии, релизы и обновление
* **Схема версий (SemVer):** `MAJOR.MINOR.PATCH` (исправление ошибок → `PATCH`, новая функция → `MINOR`, несовместимое изменение → `MAJOR`).
* **Критичные уязвимости (`[critical]`):** оформляются как обычный релиз (как правило, `PATCH`), но в описании релиза на GitHub обязательно указывается маркер `[critical]` (без учёта регистра). Если хотя бы у одного релиза новее текущей версии есть такой маркер, TUI выводит предупреждение уровня `'error'`: `⚠ Критичное обновление безопасности: vX.Y.Z (у вас vA.B.C). Обновитесь: /update`.
* **Выпуск нового релиза:**
  1. `npm version patch` (или `minor` / `major`).
  2. `git push --follow-tags`.
  3. `gh release create vX.Y.Z --generate-notes` (если релиз закрывает критичную уязвимость, добавить `[critical]` в описание релиза).
* **Раскладка директорий установки (`~/.local/share/duddy`):**
  * `~/.local/share/duddy/versions/<версия>` — директории изолированных версий с собственными зависимостями (`npm install --omit=dev`).
  * `~/.local/share/duddy/current` — атомарный симлинк на активную версию в `versions/<версия>` (`ln -sfn` + `mv -T`).
  * `~/.local/bin/duddy` — симлинк на `~/.local/share/duddy/current/bin/duddy.js`.
  * При установке новой версии в `versions/` сохраняются только текущая и одна предыдущая версия, остальные автоматически удаляются.
* **Проверка версий при запуске:** выполняется ровно один раз за запуск и только в интерактивном TUI (`checkForUpdate` в `src/ui/App.js`). В разовом/пайп-режиме проверка отключена. Переменная окружения `DUDDY_NO_UPDATE_CHECK=1` полностью отключает сетевые запросы проверки обновлений. Обновление инициируется через `duddy update` в CLI или через `/update` (алиас `/upgrade`) внутри TUI.

#### Как работает проверка (`checkForUpdate`, `src/update.js`)
1. При старте TUI один запрос `GET api.github.com/repos/rual1sher/duddy-cli/releases?per_page=30` с таймаутом 4 с. Повторных проверок и таймеров нет.
2. Черновики, пререлизы и теги не вида `vX.Y.Z` пропускаются.
3. Берётся самая новая версия. Если она не новее `pkg.version` (передаётся через `session.version`), ничего не показывается.
4. Тип обновления (`updateKind`) — по первой отличающейся цифре: `major` / `minor` / `patch`. `critical` — если `[critical]` есть в описании **любого** релиза новее текущего, а не только последнего: пользователь, пропустивший критичный фикс, должен увидеть предупреждение.
5. `updateMessage` превращает результат в заметку: `critical` → `error` (красная), `major` → `warn`, `minor` / `patch` → `info`.
6. Любая ошибка (нет сети, 404, лимит GitHub, кривой JSON) → `null`, пользователь ничего не видит. Проверка не должна мешать работе.

#### Как работает обновление (`runUpdate`, `install.sh`)
1. `detectInstall` смотрит, где лежит запущенный код. Если не внутри `~/.local/share/duddy/versions/` (git-клон, разработка), обновление отказывает с подсказкой `git pull`.
2. Определяется целевая версия (последний релиз или явно переданная; неверный формат → отказ).
3. Скачивается `install.sh` из тега `v<версия>` во временную папку и запускается `bash` с `DUDDY_VERSION=<версия>` и `cwd` во временной папке: из папки с исходниками `install.sh` включил бы локальный режим.
4. `install.sh` качает архив тега (`archive/refs/tags/vX.Y.Z.tar.gz`; если релизов нет — ветку `master`), проверяет формат версии, распаковывает в `versions/<версия>.tmp`, ставит зависимости, переименовывает в `versions/<версия>`, атомарно переключает `current`, удаляет всё, кроме новой и предыдущей версии.
5. Уже запущенный Duddy продолжает работать из старой папки, поэтому обновление его не ломает; новая версия действует после перезапуска.
6. Старая git-установка в `~/.local/share/duddy/.git` при первом запуске нового `install.sh` удаляется и заменяется раскладкой по версиям.
* `runUpdate` работает только асинхронно (`spawn`, без `execSync` / `stdio: 'inherit'`), потому что вызывается из TUI.

#### Правила для агентов: версии
* **Тип изменения определяет цифру:**

| Изменение | Префикс коммита | Цифра | Пример |
| :--- | :--- | :--- | :--- |
| Исправлен баг | `fix: ...` | PATCH (третья) | `1.2.0 → 1.2.1` |
| Новая функция, команда, флаг | `feat: ...` | MINOR (вторая), PATCH = 0 | `1.2.1 → 1.3.0` |
| Несовместимое изменение (конфиг, флаги, поведение) | `feat!: ...` или `fix!: ...` | MAJOR (первая), остальные = 0 | `1.3.0 → 2.0.0` |
| Критичная уязвимость | `fix(security): ...` | обычно PATCH + `[critical]` в описании релиза | `1.3.0 → 1.3.1` |
| Только документация, тесты, рефакторинг без изменения поведения | `docs:`, `test:`, `refactor:`, `chore:` | версия не меняется | — |

* **Агент сам версию не поднимает.** `npm version`, теги, `git push` и `gh release create` выполняются только по прямой просьбе пользователя (см. раздел 11 про git). Поле `version` в `package.json` вручную не правится — только через `npm version`.
* **В отчёте агент указывает тип изменения** (`fix` / `feat` / несовместимое / критичная уязвимость / без версии) и какую версию предлагает выпустить, например: «Тип: feat → предлагаю v1.3.0».
* **Несовместимое изменение** агент явно называет в отчёте и объясняет, что сломается у пользователей: это MAJOR, и пользователи увидят предупреждение.
* **`[critical]`** предлагается только для настоящих уязвимостей (утечка ключа, выход за рабочую папку, обход подтверждения), а не для обычных багов: красное предупреждение не должно обесцениваться.
* **Новые файлы и зависимости, которые нужны в работе, должны попадать в архив релиза.** `install.sh` ставит то, что лежит в теге на GitHub; незакоммиченные файлы в релиз не попадут.
